## 1. Введение

Цель проекта — представить знания о технологиях разработки в виде фактов и правил Prolog и использовать их для поиска подходящих технологических стеков. Стек включает язык программирования, фреймворк и СУБД.

Предметная область описана в базе знаний `solve.pl` и онтологии `Untitled.owx`. Например, в базе указано, что Gin использует Go и поддерживает PostgreSQL. На основе этих фактов можно рекомендовать сочетание Go, Gin и PostgreSQL.

Значимость проекта заключается в возможности объяснить решение: каждый предложенный вариант подтверждается фактами и условиями правил. Такой подход подходит для задач, в которых выбор определяется известными свойствами объектов и связями между ними.

## 2. Анализ требований

Система должна:

1. Хранить сведения о языках, фреймворках, СУБД и отношениях между ними.
2. Содержать правила для поиска стеков и альтернативных технологий.
3. Отвечать на запросы с переменными, перечисляя подходящие варианты.
4. Учитывать предпочтения пользователя по языку и СУБД.
5. Различать отсутствие результата и ошибку ввода.

База знаний должна содержать факты о принадлежности технологий к категориям и связи «фреймворк — язык», «фреймворк — СУБД». В `solve.pl` используются предикаты:

| Предикат | Значение |
| --- | --- |
| `language(L)` | `L` — язык или фронтенд-технология |
| `framework(F)` | `F` — фреймворк |
| `subd(DB)` | `DB` — СУБД |
| `infra(I)` | `I` — инфраструктурная технология |
| `uses_language(F, L)` | Фреймворк `F` использует язык `L` |
| `supports_db(F, DB)` | Для фреймворка `F` указана поддержка СУБД `DB` |

Онтология представляет те же категории классами, технологии — индивидами, а связи — объектными свойствами. Она дополнительно разделяет языки на подклассы `backend` и `frontend`. В исходной базе Prolog отдельные предикаты для этих направлений не заданы.

Предпочтения задаются значениями аргументов запроса. Например, `stack(go, F, postgres).` ищет фреймворк на Go с указанной поддержкой PostgreSQL. Несколько допустимых языков можно объединить условием ИЛИ, а требования к языку и СУБД — условием И.

## 3. Изучение основных концепций и инструментов

### 3.1. Обозначения в `solve.pl`

| Запись | Значение | Пример из файла |
| --- | --- | --- |
| `:-` | «Выполняется, если»: отделяет заключение правила от условий | `stack(L, F, DB) :- ...` |
| `,` между условиями | Логическое И: должны выполниться все условия | `framework(F), language(L), uses_language(F, L)` |
| `.` | Конец факта или правила | `framework(gin).` |
| `_` | Анонимная переменная: конкретное значение не требуется | `supports_db(F, _)` — связь с какой-либо СУБД |
| `\=` | Успешно, если два терма нельзя унифицировать | `F1 \= F2` исключает одинаковые найденные фреймворки |
| `\+` | Отрицание как неуспех: указанную цель не удалось доказать | `\+ supports_db(F, _)` — для данного `F` не найдена связь с СУБД |

Предикаты обозначаются именем и количеством аргументов: `language/1`, `uses_language/2`, `stack/3`. Число после `/` называется арностью.

### 3.2. Как читается правило

```prolog
framework_language(F, L) :-
    framework(F),
    language(L),
    uses_language(F, L).
```

Слева от `:-` находится голова правила — что нужно получить. Справа находится тело — условия получения результата. Правило читается: «`L` является языком фреймворка `F`, если `F` — фреймворк, `L` — язык и `F` использует `L`».

Условия проверяются слева направо.

### 3.3. Как подбираются значения

При сопоставлении `uses_language(F, go)` с фактом `uses_language(gin, go)` переменная `F` получает значение `gin`. Это унификация. Поиск с возвратом позволяет найти следующий подходящий факт — `uses_language(chi, go)` — и получить второй ответ, `F = chi`.

В правиле `same_language` общая переменная `L` требует один язык для двух фреймворков:

```prolog
uses_language(F1, L),
uses_language(F2, L),
F1 \= F2.
```

Первые два условия находят фреймворки, последнее исключает пару фреймворка с самим собой. Для `gin` на Go альтернативой становится `chi` на Go.

В правиле `no_db_info` сначала выбирается конкретный фреймворк, затем проверяется отсутствие сведений:

```prolog
no_db_info(F) :-
    framework(F),
    \+ supports_db(F, _).
```

Для `chi` связь с СУБД не найдена, поэтому правило выполняется. Для `gin` есть `supports_db(gin, postgres)`, поэтому правило не выполняется. Здесь `\+` означает отсутствие доказательства в базе, а не доказанную невозможность работать с СУБД.

## 4. Реализация системы искусственного интеллекта (системы поддержки принятия решений)

### 4.1. Создание правил и логики вывода на основе онтологии

Реализация состоит из трёх функций:

| Функция | Назначение |
| --- | --- |
| `load_ontology` | Читает XML и извлекает классы, подклассы и объектные связи |
| `recommend` | Находит сочетания фреймворка, языка и СУБД по заданным условиям |
| `main` | По очереди спрашивает направление, язык и, для бэка, СУБД; выводит результат таблицей |

Для чтения XML используется `xml.etree.ElementTree`. Данные сохраняются в двух словарях: `classes` содержит множества объектов каждого класса, `relations` — связи между объектами. Например:

```python
classes["backend"] = {"go", "java", "ruby"}
relations["uses_language"]["gin"] = {"go"}
relations["support_db"]["gin"] = {"postgres"}
```

По связям `SubClassOf` объекты классов `backend` и `frontend` добавляются в `language`. Парсер рассчитан на структуру исходного файла; сложные аксиомы OWL не обрабатываются.

Программа задаёт отдельные вопросы. Сначала пользователь выбирает бэк или фронт, затем программа предлагает языки выбранного направления, для которых в онтологии есть фреймворки. Для бэка дополнительно уточняется база данных:

```text
Что разрабатываете — бэк или фронт? бэк
Доступные языки: go, java, ruby
Какой язык предпочитаете? go
Базы данных: mongodb, mysql, oracle, postgres, redis
Можно ответить «любая» или «не нужна».
Какая база данных нужна? postgres
```

Каждый ответ проверяется по предложенным вариантам; регистр и пробелы по краям не учитываются. Для фронта после выбора языка сразу выводятся фреймворки, вопрос о базе данных не задаётся.

Логика выбора реализована условиями в `recommend`:

1. Кандидат должен принадлежать классу `framework` и иметь связь `uses_language` с выбранным языком.
2. Выбрать можно только язык выбранного направления: `backend` для бэка или `frontend` для фронта.
3. Если СУБД требуется, у того же фреймворка должна быть связь `support_db` с подходящей СУБД из класса `subd`.

Условия выбора объединяются логическим И. Для бэка ответ `любая` допускает любую известную связь с СУБД, а `не нужна` исключает проверку СУБД. Для фронта эта проверка всегда пропускается. Так правила отбора применяются непосредственно к извлечённым фактам.

Для приведённого запроса результат имеет вид:

```text
Фреймворк      | Язык     | База данных
----------------------------------------
gin            | go       | postgres
```

### 4.2. Проверка, отладка и эффективность

Проведена ручная проверка консольной программы на следующих сценариях:

| Ввод | Наблюдаемый результат |
| --- | --- |
| `бэк`, язык `go`, СУБД `postgres` | Gin на Go с PostgreSQL |
| `бэк`, язык `java`, СУБД `любая` | Spring на Java с MySQL и PostgreSQL |
| `фронт`, язык `js` | Angular, React и Vue; вопрос и столбец базы данных отсутствуют |
| `бэк`, язык `go`, СУБД `mysql` | Сообщение об отсутствии подходящих вариантов |
| `сервер`, затем `бэк`; `python`, затем `go`; `post`, затем `postgres` | Все три неверных ответа отклонены, соответствующие вопросы повторены; после исправления получен Gin на Go с PostgreSQL |

Отладка выполнялась сопоставлением вывода с фактами онтологии. Например, Gin появляется при выборе PostgreSQL благодаря связи `support_db(gin, postgres)`, а Chi не появляется, поскольку такой связи для него нет.

Ошибки чтения файла и синтаксиса XML обрабатываются сообщением. Неизвестные языки и СУБД отклоняются; пустая выборка сопровождается сообщением `Подходящих вариантов не найдено.` EOF и Ctrl+C завершают диалог.

Для эффективности XML читается один раз перед диалогом. Извлечённые данные хранятся в словарях и множествах; направление и язык проверяются до перебора СУБД. Результаты сортируются перед выводом, поэтому порядок строк воспроизводим.

## 5. Оценка и интерпретация результатов

### 5.1. Примеры запросов к базе знаний

В таблице приведены ожидаемые ответы по фактам и правилам `solve.pl`; порядок перечисления здесь не учитывается.

| Запрос | Ожидаемый результат |
| --- | --- |
| `language(go).` | `true` |
| `uses_language(F, go).` | `F = gin`; `F = chi` |
| `framework_language(F, js).` | `F = react`; `F = vue`; `F = angular` |
| `can_use_db(gin, postgres).` | `true` |
| `stack(go, F, postgres).` | `F = gin` |
| `stack(go, F, mysql).` | `false`: подходящий стек не доказан |
| `same_language(gin, F).` | `F = chi` |
| `alternative_db(spring, postgres, DB).` | `DB = mysql` |
| `no_db_info(chi).` | `true`: в базе нет сведений о СУБД для Chi |

Запрос `stack(L, F, DB).` даёт четыре сочетания:

- Java — Spring — PostgreSQL.
- Java — Spring — MySQL.
- Go — Gin — PostgreSQL.
- Ruby — Rails — Redis.

Результаты объясняются соединением фактов `uses_language` и `supports_db`. Добавление фактов о новом фреймворке позволяет включить его в поиск без изменения правила `stack/3`.

### 5.2. Сравнение базы знаний и онтологии

| Знание | Представление в Prolog | Представление в онтологии |
| --- | --- | --- |
| Gin — фреймворк | `framework(gin).` | Индивид `gin` принадлежит классу `framework` |
| Gin использует Go | `uses_language(gin, go).` | Объектное свойство `uses_language` связывает `gin` с `go` |
| Gin поддерживает PostgreSQL | `supports_db(gin, postgres).` | Объектное свойство `support_db` связывает `gin` с `postgres` |

Запрос `uses_language(F, go).` соответствует поиску субъектов отношения `uses_language`, объектом которого является `go`: в обоих источниках такими фреймворками являются Gin и Chi. Для выбора стека требуется дополнительно найти связь того же фреймворка с нужной СУБД.

В Prolog связи описаны предикатами, а новые сочетания находятся выполнением правил, унификацией и поиском с возвратом. В онтологии знания представлены классами и объектными свойствами. Свойство поддержки СУБД в OWL называется `support_db`, а предикат Prolog — `supports_db`. В OWL заданы подклассы `backend` и `frontend`; в `solve.pl` принадлежность к `language` записана непосредственно фактами.

Исходные данные отличаются: в `solve.pl` есть `supports_db(rails, redis)`, в `Untitled.owx` такой связи нет. Поэтому правило `stack/3` даёт четыре ожидаемых решения по базе Prolog, а явные отношения онтологии подтверждают три соответствующих сочетания. Это различие данных. Для Ruby с Redis в онтологии отсутствует подтверждающая связь.

### 5.3. Оценка решения и возможности развития

База знаний содержит факты и правила, позволяющие искать стеки, общие технологии и альтернативы. Рекомендации можно объяснить через конкретные условия правил. Пользователь уточняет ограничения, изменяя аргументы запросов.

Ограничения связаны с полнотой знаний: не учитываются версии, производительность, стоимость и сложность освоения технологий. Инфраструктурные объекты записаны в базе, но не связаны со стеками.

В дальнейшем можно согласовать сведения Prolog и OWL, добавить критерии выбора, правила ранжирования и связи с инфраструктурой.

## 6. Заключение

В проекте знания о технологиях разработки представлены фактами и правилами Prolog. На их основе сформулированы запросы для выбора стеков, поиска альтернативных фреймворков и СУБД, а также выявления отсутствующих сведений.

Преимущество Prolog для данной задачи — возможность описать условия решения декларативно: задать факты и правила, после чего получать подходящие значения переменных через запросы. Обоснование рекомендации следует из выполненных условий.

Онтология предоставляет другое представление той же предметной области через классы, индивиды и отношения. Подобная система применима к учебным каталогам технологий и подбору компонентов, совместимость которых описана явными фактами.
